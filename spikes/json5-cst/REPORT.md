# Spike 002 T4 — JSON5 style-preserving edits (UNK-012)

**Result:** Option F, our own JSON5 parser, passes **20 of 20** cases; the best packages,
`@humanwhocodes/momoa` and `jsonc-eslint-parser`, pass 19. Under UNK-012's evidence rule ("pick the
option with the most of the 20 spike cases passing; ties go to fewer runtime deps; own parser if no
package passes ≥ 18") the decision is **own parser**. Recorded as ADR-009.

## Question and hypothesis

UNK-012 asks whether an existing package can back style-preserving JSON5 edits or whether `core`
needs its own parser. HYPOTHESIS (from the row): `jsonc-parser` cannot tokenize JSON5-only syntax
and `json5` keeps no positions. Both halves are confirmed below (options A and B).

## Method

1. **Cases first.** The 20 cases in [`cases/`](cases/) (input, one-op patch, hand-written expected
   bytes) were committed in `c27d2cd` before any option ran. Their conventions are in
   [`cases/README.md`](cases/README.md). Each one exercises named JSON5 features: unquoted, reserved-word
   and `\u`-escaped keys, single quotes and escaped quotes, hex, `±Infinity`, `NaN`, leading and
   trailing decimal points, explicit `+`, line continuations, astral characters, CRLF, tabs,
   U+00A0 whitespace, unescaped U+2028 in a string, line and block comments, comment markers inside
   strings, single-line and multi-line containers, trailing commas on and off. A sanity check with
   the reference `json5` package confirmed that every `expected.json5` parses to the input's data
   with the patch applied.
2. **One edit engine for every tree.** [`engine.ts`](engine.ts) applies `add`, `replace` and
   `remove` per spec 002 R1–R10 and UNK-008 from a minimal tree (container and key/value spans in
   UTF-16 offsets, decoded key names). Each option maps its parser's output to that tree, so a
   pass or fail measures the parser: whether it accepts the input, whether its offsets are right,
   and whether it decodes keys. The engine also re-scans every gap between nodes and fails if it
   finds anything but whitespace, commas and comments, which catches wrong offsets.
3. **Options measured.** Every npm package found whose description claims JSON5 support with
   source positions, plus the two the row names, plus our own parser:

   | ID | Option | How it edits |
   |---|---|---|
   | A | `jsonc-parser` 3.3.1 | `parseTree`; any parse error fails the case |
   | B | `json5` 2.2.3 | no positions: parse, change data, `JSON5.stringify` with the file's indent and quote |
   | C | `@humanwhocodes/momoa` 3.3.13 | `parse(text, {mode: 'json5', ranges: true})` |
   | D | `jsonc-eslint-parser` 3.3.0 | `parseJSON(text, {jsonSyntax: 'json5'})` |
   | E | `@croct/json5-parser` 0.2.2 | `JsonParser.parse` node locations |
   | E′ | `@croct/json5-parser` 0.2.2 | the package's own style-learning writer (`set`/`delete`/`splice`, `toString`) |
   | F | own parser, [`own-parser.ts`](own-parser.ts) | recursive descent written from the JSON5 1.0.0 spec |

   Not measured, because their npm descriptions name JSON only, or they wrap another option:
   `json-to-ast`, `json-cst`, `json5-parser` (wraps `json5`), `json5-writer` (wraps `jscodeshift`).
4. **Pass** = output byte-equal to `expected.json5` (`run.ts`, strict `===`).

## Results (20 cases)

Generated by `run.ts`; full per-case table and every failure reason in
[`results.md`](results.md), raw data in [`results.json`](results.json).

| Option | Passed (of 20) | Runtime packages it would add (transitive, with license) |
|---|---|---|
| A `jsonc-parser` 3.3.1 | 1 | 1: jsonc-parser (MIT) |
| B `json5` 2.2.3 | 6 | 1: json5 (MIT) |
| C `@humanwhocodes/momoa` 3.3.13 | 19 | 1: @humanwhocodes/momoa (Apache-2.0) |
| D `jsonc-eslint-parser` 3.3.0 | 19 | 4: jsonc-eslint-parser (MIT), acorn (MIT), eslint-visitor-keys (Apache-2.0), verkit (MIT) |
| E `@croct/json5-parser` 0.2.2 | 16 | 2: @croct/json5-parser (MIT), @croct/json (MIT) |
| E′ `@croct/json5-parser` 0.2.2, own writer | 13 | 2: as E |
| **F own parser** | **20** | **0** |

Why each package misses (from `results.md`):

- **A** rejects every input with JSON5-only syntax (`InvalidSymbol`, `PropertyNameExpected`); it
  passes only case 02, which is plain JSON. Confirms the hypothesis.
- **B** loses comments, hex, `+Infinity`, line continuations, key quoting and single-line layout,
  because it has no positions. Confirms the hypothesis.
- **C** rejects reserved words as unquoted keys (case 17, `null: 1`), which JSON5 allows
  (JSON5Identifier is ES5 IdentifierName; the reference `json5` parses it).
- **D** rejects a `\u`-escaped unquoted key (case 18, `abc: 1`), which JSON5 allows
  (IdentifierName includes UnicodeEscapeSequence; the reference `json5` parses it).
- **E** counts offsets in code points, not UTF-16 units, so edits after astral characters land in
  the wrong place (case 07: `cou2t: 1`); it also rejects cases 17, 18 and 20 (U+2028 in a string).
- **E′** additionally places comments and commas by its own rules, not spec 002's (cases 10, 11,
  13) and writes new strings with `"` where the file's majority is `'` (case 19).

## Decision under the evidence rule

- Most cases passing: **F with 20**. No tie, so the runtime-dependency tie-break does not apply,
  and the ≥ 18 floor is not reached (C and D pass 19).
- **Reading checked, flagged for the Reviewer.** The rule says "option", and UNK-012's description
  lists the own parser as one of the options ("existing CST package vs own parser"); the
  architecture snapshot calls the own parser the "proposed default"
  (`docs/research/architecture.md` line 67). A narrower reading, where only packages compete and
  the own parser is only the fallback below 18, would pick **C** (19, tied with D, fewer runtime
  packages: 1 vs 4). This report follows the rule's wording. The outcome holds when case 18,
  whose input upstream json5-tests still keeps under `todo/`, is left out: F 19, D 19, C 18, and
  the tie-break picks F (0 runtime packages vs 4).

## Consequences for 002 T5

- Move `own-parser.ts` into `packages/core` as the JSON5 tree builder (no new runtime
  dependency, nothing to add to `check:licenses`) and give it unit tests with json5-tests as a
  conformance fixture.
- The engine here is spike code. T3/T5 build the real edit layer against the golden corpus
  (002 T1), which may settle the spike-local readings in `cases/README.md` differently.
- `json5` stays the reference implementation for data (`parse(...).data`) and for `stringify`.

[`package.json`](package.json) and `pnpm-lock.yaml`. None of these packages ships: the spike
package is `private` and only has `devDependencies`.
